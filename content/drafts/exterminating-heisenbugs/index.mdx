In the [last post](../no-room-for-bugs/) I argued that software correctness is about shrinking the gap between the floor (what the language guarantees automatically) and the ceiling (a full formal proof the program meets its spec), with screens—testing of various kinds—catching whatever still lives in the gap.

One category of bug eats a disproportionate share of debugging time, resists ordinary testing, and routinely slips through the screen. These are the ones that depend on the environment's randomness: a packet arrives slightly late, a thread is scheduled a particular way, a disk flushes at an unlucky moment, and the system misbehaves in a way that doesn't reproduce on your laptop. These are [*heisenbugs*](https://en.wikipedia.org/wiki/Heisenbug): the bugs that page you on a Tuesday and are never seen again.

The structural reason heisenbugs are hard is simple. The program's behavior silently depends on choices the environment made, and nobody wrote those choices down. The test harness didn't know those choices existed, so it never reproduced them.

The way to make progress is to stop letting the environment make those choices silently. There are two serious approaches in the wild, and they intervene at different levels: the runtime, and the language itself.

---

## Seize control of the runtime

If the environment's randomness is the problem, one answer is to take the randomness away from the environment.

[Shuttle](https://github.com/awslabs/shuttle), [Turmoil](https://github.com/tokio-rs/turmoil), and [Antithesis](https://antithesis.com) all do this, in different ways. They replace the operating system or runtime with an instrumented version that controls the scheduler, the clock, and the network. Every source of non-determinism goes through their harness. The harness runs the program under test, and if a bug surfaces, it can rewind and replay the exact unlucky schedule that produced it, deterministically. Antithesis takes this furthest: it runs the entire system inside a deterministic hypervisor, so even disk timing and system calls are reproducible.

What these tools give you is reproducibility of the environment's randomness, which is a big deal: a reproducible bug is a bug you can fix. What they don't give you—at the language level, anyway—is any help identifying *where in your code* the randomness matters. The harness has to explore whatever the scheduler can do, because it doesn't know which code paths are secretly order-sensitive and which aren't. Your test ends up chasing coverage of all those possibilities, often blindly. The screen has gotten remarkably good at this, but it's still a screen.

---

## Eliminate silent dependence on randomness

The second approach attacks the problem one level higher: refuse to let programs silently depend on environment randomness in the first place.

This is what [Hydro](https://hydro.run) does. Every source of non-determinism that could perturb the program's behavior has to be acknowledged in the type system. If a stream of messages reaches an operator that cares about ordering, the type system either guarantees the operator is commutative (and therefore order-insensitive, and therefore deterministic), or demands that the ordering uncertainty be wrapped in a `nondet!` block (and therefore made visible to the compiler, the programmer, and the simulator). There is no silent dependence on the environment's mood.

With non-determinism made explicit, Hydro's built-in model checker—[HydroSim](https://hydro.run/docs/hydro/reference/simulation/)—can be surgical. It takes each `nondet!` point and systematically explores the environment's choices there: every schedule, every delivery pattern, every failure the environment is permitted to produce (up to the practical bounds of model checking). Outside the `nondet!` blocks, the program is eventually deterministic—it will converge to the same answer no matter what the network did. Inside, every answer the environment can elicit is on the table during testing.

The move is subtler than it sounds. The screen's job gets dramatically easier when the compiler tells you precisely where the sources of randomness live. Runtime-level testers have to probe the whole program because they don't know. HydroSim doesn't have to probe anywhere outside `nondet!`: the type system wrote the map.

---

## Where each wins

Neither approach alone eliminates heisenbugs. Each catches a different slice.

**Runtime-level testers** are powerful when the program under test isn't written in a language with explicit non-determinism tracking. If you have a Go or Rust service that races in interesting ways, Shuttle gives you deterministic replay. Antithesis extends the same idea to arbitrary systems under test, which is a big deal if you can't change the language the system is written in. The price is coverage: you're sampling an unknown space of unlucky schedules, hoping the sampler reaches the one that triggers your bug.

**Language-level elimination** is the pre-emptive move: refuse to let the bug be written in the first place, and tightly bound the places where non-determinism can still live. It requires buying into the language, which is a bigger commitment than running a test harness. The payoff is that most heisenbugs become impossible to express, and the ones that remain are confined to clearly marked regions where tests know to focus.

My own bet is on the second approach, which is why I spend my time on Hydro. But the honest answer is that the two combine well: Hydro narrows the places where non-determinism can live, and a runtime-level tester can still ride underneath to shake out whatever bugs survive in the surrounding stack (OS, hardware, external services).

Heisenbugs don't go away. But each of these approaches shrinks the subset of them that can survive long enough to page someone.
